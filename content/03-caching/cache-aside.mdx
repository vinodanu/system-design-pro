# Caching and Cache-Aside

> **Difficulty:** Beginner → production engineering. **Goal:** Develop the intuition, understand implementation choices, and explain tradeoffs in interviews.

## 1. Why this matters

A cache stores frequently used results closer to consumers to reduce backend work.

## 2. Mental model

On a cache miss, read from the database then populate the cache. On writes, invalidate or update affected entries. TTL avoids keeping data indefinitely.

## 3. Explore the concept

Sketch a small system with two clients and three backend nodes. Change one assumption (load, latency, or a server failure), then trace how the behavior changes. Explain what should remain correct and which metric will get worse.

## 4. Java / Spring Boot deep dive

Spring Cache with Redis can implement cache-aside, but think through transaction boundaries and serialization. With WebFlux, prefer reactive Redis clients and avoid blocking cache APIs on event-loop threads.

## 5. Production tradeoffs

Cache stampedes, hot keys, stale results and cache/database consistency are major risks. A cache is not a source of truth by default.

## 6. Check your understanding

**Question:** Why can a cache outage overload your database?

**Answer:** Requests that formerly hit the cache can all become database reads, causing a sudden traffic surge.

## 7. Try it in a project

Build a small Spring Boot service that demonstrates this principle. Record a baseline (latency, throughput, correctness), change one variable, and compare the results. Document what your measurements actually prove rather than assuming a benchmark result.
