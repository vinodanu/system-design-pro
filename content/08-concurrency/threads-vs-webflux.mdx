# Java Threads vs Spring WebFlux

> **Difficulty:** Beginner → production engineering. **Goal:** Develop the intuition, understand implementation choices, and explain tradeoffs in interviews.

## 1. Why this matters

High concurrency means handling many overlapping operations efficiently, not necessarily doing more CPU work at once.

## 2. Mental model

Thread-per-request can be straightforward but expensive when many threads wait on I/O. Non-blocking pipelines free event-loop threads to work on other requests.

## 3. Explore the concept

Sketch a small system with two clients and three backend nodes. Change one assumption (load, latency, or a server failure), then trace how the behavior changes. Explain what should remain correct and which metric will get worse.

## 4. Java / Spring Boot deep dive

Spring MVC with virtual threads and Spring WebFlux are both viable depending on workload. Profile blocking calls; WebFlux requires non-blocking end-to-end I/O to realize its advantages.

## 5. Production tradeoffs

Reactive code adds operational and debugging complexity. CPU-bound work still needs CPU time; blocking JDBC on the event loop defeats non-blocking benefits.

## 6. Check your understanding

**Question:** Does WebFlux make CPU-heavy code faster?

**Answer:** No. It primarily helps manage concurrency when workloads spend time waiting for I/O.

## 7. Try it in a project

Build a small Spring Boot service that demonstrates this principle. Record a baseline (latency, throughput, correctness), change one variable, and compare the results. Document what your measurements actually prove rather than assuming a benchmark result.
