# Design a Payment System

> **Difficulty:** Beginner → production engineering. **Goal:** Develop the intuition, understand implementation choices, and explain tradeoffs in interviews.

## 1. Why this matters

Payments prioritize correctness, auditable state transitions and safe retry behavior.

## 2. Mental model

Use idempotency keys, a durable transaction record, webhooks, reconciliation and an explicit state machine. Avoid pretending distributed workflows are one atomic SQL transaction.

## 3. Explore the concept

Sketch a small system with two clients and three backend nodes. Change one assumption (load, latency, or a server failure), then trace how the behavior changes. Explain what should remain correct and which metric will get worse.

## 4. Java / Spring Boot deep dive

In Spring Boot, place idempotency checks and business transitions inside database transactions where feasible. Use the outbox pattern to reliably publish events after commits.

## 5. Production tradeoffs

Duplicate callbacks, provider timeouts, partial success and refunds require compensating and reconciliation workflows.

## 6. Check your understanding

**Question:** Why are idempotency keys critical?

**Answer:** Clients and gateways may retry; a stable key helps prevent one intent from creating duplicate charges.

## 7. Try it in a project

Build a small Spring Boot service that demonstrates this principle. Record a baseline (latency, throughput, correctness), change one variable, and compare the results. Document what your measurements actually prove rather than assuming a benchmark result.
